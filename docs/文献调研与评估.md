# PreCex：反例驱动的综合前 RTL 缺陷定位与修复智能体（文献调研与评估）

> 项目名：PreCex（Pre-synthesis + Counterexample）

> 作者：Toylog
> 版本：v1.0（2026-08-03）
> 调研对象：《项目方案.md》v1.1 的 6 组件体系
> 数据来源：本地 26 篇综述资产（02_26篇论文-AI_for_EDA路线图）+ 2025–2026 最新网络文献检索

---

## 1. 调研范围与方法

按项目方案的核心链条（**反例语义化 → 定位 → 切片修复 → 形式再验证 → 验证充分性**）分四个方向检索：

| 方向 | 对应组件 | 检索重点 |
| --- | --- | --- |
| 方向一：形式验证失败根因分析 / 反例理解 | CexSemantizer（核心创新） | counterexample-driven debugging、formal verification root cause analysis |
| 方向二：LLM RTL 调试与修复 | LocalRepairer | Verilog bug localization / repair |
| 方向三：断言生成与验证充分性 | Verifier | SVA generation、mutation testing、vacuity |
| 方向四：数据集与评测基准 | BugBench-PS / harness | RTL debug benchmark、工具执行裁决 |

## 2. 文献地图与逐篇评估

### 2.1 方向一：形式验证失败根因分析与反例理解（竞争最相关区）

| 文献 | 出处 | 核心方法 | 与本项目关系 | 强度评估 |
| --- | --- | --- | --- | --- |
| **FVDebug**（NVIDIA，Bai et al.）[arXiv:2510.15906] | 2025-09 | 失败轨迹→因果 DAG；Graph Scanner 批量 LLM 扫描可疑节点；Insight Rover agentic 叙事；Fix Generator 给出修复；含 2 个工业级反例案例 | **直接竞争基线**：与 CexSemantizer 高度同向 | 强（工业背书），但依赖商业工具链，且**无三设置消融、无验证充分性量化** |
| **GROVE**（NVIDIA，Bai & Ren）[arXiv:2511.17833] | 2025-11 | 断言失败调试的 LLM 组织分层知识树；训练时用 model-checking 验证知识项、测试时预算感知检索；pass@1/pass@5 一致提升 | 竞争+互补：我们"消费反例"，GROVE"沉淀知识" | 中强；知识树可借鉴为后续扩展 |
| **Open-Source LLM-Driven Formal Verification**（Tran）[arXiv:2607.28877] | 2026-07 | **与我们的工具链完全一致**：Yosys/SymbiYosys/Z3 + LLM 反例引导迭代修复；k-induction 证明或预算耗尽停止；6 benchmark 仅 1 个可靠修复 | **最直接的先导工作与基线**：证明"开源链路+反例引导"可行但成功率低，正是我们的机会 | 可行性研究（案例级），失败模式分析价值高 |
| **FormalRTL**（CUHK/Huawei）[formind.netlify.app] | 2025 | 软件参考模型作形式规格，规划/综合/等价性检查闭环；含"反例简化器"（只显示问题函数与失配信号） | 参考模型路线与我们不同（我们用断言+反例，不用 C 参考模型）；反例简化思路可借鉴 | 中强（工业级 datapath 定位） |
| **ChipAgents RCA**（商业）[semiwiki 2026-07] | 2026 | waveform-understanding engine + prover-verifier agent 对 + self-consistency 排序；能定位 3 周期竞争条件；工业落地（Whalechip） | 证明"跨周期根因分析"是工业真痛点；商业黑盒，无消融细节 | 商业参照，不可直接对比但证明问题真实性 |

**方向一评估**：2025Q3 起竞争**快速收窄**。FVDebug 已覆盖"反例→因果图→根因→修复"全链；但存在明确缺口——**开源全链路**、**跨周期 bug 专项**、**三设置消融方法论（原始日志 vs 结构化 vs 反例语义化）**、**验证充分性量化（mutation/vacuity）**均未被上述工作覆盖。这与本项目方案高度吻合。

### 2.2 方向二：LLM RTL 调试与修复（竞争饱和区）

| 文献 | 出处 | 核心方法 | 与本项目关系 |
| --- | --- | --- | --- |
| **VeriPilot**[arXiv:2606.23759] | 2026-06 | 黄金参考模型 + CDFG 信号追踪，CVDP 上 GPT-4o 修复率 54.3%→85.71% | 通用修复 SOTA 之一，非反例驱动 |
| **VeriDebug**[arXiv:2504.19099] | 2025-04 | 对比嵌入 + 引导修正，Loc+Type 联合模型 Acc@1 64.7% | 专用微调路线，与 LLM-API 方案不同 |
| **RTLFixer**（综述内） | — | RAG 修复语法错误 | 基线参考 |
| **Fixbench-RTL**[asianhost'25] | 2025 | 语法/功能/安全三域调试 benchmark，含 bug 注入框架 | 基准参考 |
| **HDL-FixBench**[ICLR'26 投稿] | 2025-09 | 仓库级 57 实例（OpenTitan/CVA6/Ibex），最好模型 40.3%；**已被 ICLR 2026 拒稿** | **教训来源**（见 4.2） |

**方向二评估**：竞争饱和，纯"让 LLM 修 RTL"无差异化空间。本项目必须坚持"反例驱动"定位，避免滑入通用修复。

### 2.3 方向三：断言生成与验证充分性

| 文献 | 出处 | 核心方法 | 与本项目关系 |
| --- | --- | --- | --- |
| **AssertLLM**（HKUST）[ASPDAC'25] | 2025-01 | 从规格 NL+波形图生成 SVA | 断言生成成熟基线 |
| **AssertLLM2**（HKUST）[arXiv:2605.27472] | 2026-05 | 83 设计断言 benchmark；**bug-hunting 设置（输入 buggy RTL 暴露缺陷）**；mutation-based bug detection 评估 | **与我们的 L3 数据构造与 Verifier 评测同构，直接引用** |
| **AssertGen**（CAS）[ATS'25] | 2025-09 | CoT 提取验证目标 + 跨层信号桥接；mutation testing 覆盖率评估 | Verifier 评测方法参考 |
| **LASSO**（UF）[MLCAD'25] | 2025 | 安全属性生成 + **非空洞性（vacuity）** + 覆盖率反馈 + 检出 OpenTitan 5 bug | **vacuity 检查参考** |
| **ChatSVA / AgileAssert / CoverAssert**（26 篇内） | 2025 | 多阶段 SVA 生成、关键信号筛选、coverage 回灌 | 已入项目方案 6.4 |
| **LintLLM**（NUDT）[GLSVLSI'25] | 2025-06 | LLM lint + **mutation-based 缺陷注入** benchmark | mutation 注入器参考 |

**方向三评估**：断言**生成**饱和；本项目做的是"**消费反例 + 量化验证充分性**"（mutation/vacuity/假阳性率），角度不同。AssertLLM2 与 LintLLM 证明我们的评测方法在文献中有成熟先例。

### 2.4 方向四：数据集与评测基准

- **工具执行裁决被认可**：Rule2DRC（ICML 2026，13,921 版图执行比对）、PostEDA-Bench（145 任务 DRC/PPA）——支持本方案"以工具执行为裁决"的设计。
- **工程语义数据**：OpenRTLSet（13.1 万样本）、EDA-Schema-V2（多模态 schema）、ChipLingo（RAG 训练）——schema 设计参考。
- **HDLFixBench 拒稿教训**：规模小（57）、多样性不足、patch 阈值争议、缺非 LLM 基线、污染风险——本项目数据集必须规避。

## 3. 直接基线清单（实验必须对比）

| 基线 | 对比价值 | 我们的差异化 |
| --- | --- | --- |
| 2607.28877 开源反例引导 pipeline | 同工具链（Yosys/SBY/Z3），成功率仅 1/6 | 加入**反例语义化层**（它把原始反例直接喂 LLM） |
| FVDebug 因果图根因分析 | 反例理解 SOTA | 开源全链路 + 跨周期专项 + mutation/vacuity 量化 |
| GROVE 知识树检索 | 断言失败调试知识管理 | 我们不依赖历史知识库，单样本闭环 |
| VeriPilot / VeriDebug | 定位修复 SOTA | 反例驱动 vs 参考模型/嵌入 |
| 三设置 A/B/C | 本方案方法论贡献 | FVDebug 等均未做此消融 |

## 4. 对本项目方案的评估结论

### 4.1 创新点评估：成立，但定位需升级

- "反例语义化"从**空白区**降级为**快速收窄的竞争区**（FVDebug 2025-09 已先行）；
- 创新点需重构为三支柱组合：
  1. **开源全链路**（FVDebug 依赖商业工具，我们是纯开源可复现）；
  2. **三设置消融方法论**（A 原始日志 / B 结构化证据 / C 反例语义化，文献中无此对照）；
  3. **跨周期 bug 专项 + 验证充分性量化**（mutation score / 非空洞率 / 假阳性率，FVDebug 未涉及）。
- 论文中须显式与 FVDebug 的因果图做对比实验，否则审稿风险高。

### 4.2 方案需要修订的点（吸收调研结论）

1. **主实验基线扩充**：A/B/C 之外增加"FVDebug 式因果图摘要"设置 D（若可实现简化版）；
2. **L3 数据构造与评测**：引用 AssertLLM2 bug-hunting 设置与 LintLLM mutation 注入法作为方法学先例；
3. **数据集防拒稿**：样本 ≥30、错误类型多样性矩阵、污染检查（规避 GPT/LLM 训练语料中的常见模块）、补非 LLM 基线（纯规则/prompt 无工具）;
4. **失败模式分析**：采用 2607.28877 的 4 类分类（bounded-cover vacuity / spec ambiguity / temporal-logic / multi-property pressure）作为分析框架起点；
5. **工程预研**：先做 3 例跨周期 bug 的"反例语义化 vs 原始反例"快速验证（对应原 Gate-2），确认增益后再全量投入。

### 4.3 可行度结论更新

- 整体维持**中高**，但创新点风险由"中"上调为"中高"（FVDebug/GROVE 已先行，审稿对比压力增大）；
- 缓解路径明确：三支柱差异化 + 显式对比 + 快速预研 Gate。

## 5. 结论与建议

1. 主攻方向（反例驱动的跨周期 RTL 修复）**保持不变，问题真实、工业已背书**；
2. 按 4.2 修订项目方案（新增基线 D、数据防拒稿条款、预研 Gate、失败模式框架）；
3. 新增动作：M0.5 三例预研（反例语义化增益验证）应在 M1 全量构建前执行。
