
# 交叉视角评审报告（Reviewer 3）

> 评审依据：academic-paper-reviewer（full 模式，Phase 1 独立评审之一）。只读评审，未修改稿件。

## 总体评价与评分

**评分：46/100。** 论文的工程价值（开源、可复现、充分性审计）真实存在，但对目标读者（硬件验证工程师/EDA 研究者）而言，"证据表征消融"的命题性结论已被泄漏问题推翻；在数据卫生与判据叙事修正之前，读者无法信任其核心比较。

## 优点

1. 与软件工程 LLM 修复（SWE-bench 类）形成可迁移的对照：工具执行裁决 + 成本记账 + 断点续跑，是硬件侧少见的严谨工程化。
2. "判据必须先验证 golden"的实践规则，对任何想用形式验证做自动修复评测的人都有直接可操作性。
3. 开源承诺（如果随论文发布代码/数据/账本）对工业转化有吸引力；变异+空泛+T2 审计组合在同类论文里是加分项。

## 主要问题

### P1-1：对目标读者，"so what"不清晰
- 读完论文，硬件验证工程师能带走什么？"B 证据最好"——已经站不住；"100% 修复"——判据太弱不可信；"判据教训"——对不搞自动修复评测的人价值有限。
- 更有价值的产出其实是：**一个可复用的、带数据卫生与判据卫生的 LLM-RTL 修复评测协议 + 开源工具链**。论文应把"协议"而不是"某设置的精度"作为卖点。

### P1-2：跨学科借鉴不足（数据卫生是 SWE-bench 社区的成熟教训）
- LLM 代码修复领域对 benchmark contamination 已有大量讨论（HumanEval/SWE-bench 的泄漏检测、去污染流程、时间戳隔离）。论文引用了 HDL-FixBench 被拒，却没有把自身泄漏检测方法（3 来源扫描、行号不变消毒、prompt 逐字节对比）与这些实践对齐，显得"知而不察"。
- 建议：在数据卫生小节引用并对比 SWE-bench 去污染实践，把 PreCex 的 strip_ground_truth 工具作为领域贡献发布。

### P1-3：基本假设挑战——"给 LLM 更好的证据"是否值得独立成文
- 干净数据下 A（原始日志）在 DS 上反而最好，说明"证据表征"效应远弱于模型/数据卫生效应。这本身回答了"证据表征是否独立成文"——**结论是：它不是一个稳定的独立变量**。论文要么把它降级为探索性消融，要么把研究问题改写成"什么因素（模型/证据/卫生）主导 LLM-RTL 修复性能"。
- 修改方向：把叙事从"我们改进了证据表征"改为"我们测出了证据表征效应的边界条件"。

### P1-4：安全与伦理讨论不足
- LLM 自动生成 RTL 补丁并"自动验证通过"，若用于工业，存在"浅深度 BMC 掩盖真实缺陷"的安全风险。论文局限性有提及，但应上升为独立讨论（何时可以信任自动修复、人类复核职责）。
- LLM 评分替代真人（人工可解释性评分协议）本身是探索性方法，论文已诚实标注 ICC 低，可保留。

## 可操作修改建议

1. 把核心卖点从"证据表征精度"改为"可复用的评测协议 + 开源工具链 + 双卫生教训"。
2. 数据卫生小节对齐 SWE-bench 社区实践并发布 strip_ground_truth 工具。
3. 增加"何时信任自动修复"的讨论段（安全边界）。
4. 摘要与结论的 so-what 重写：读者能带走"协议与教训"，而非"B 最好"。
